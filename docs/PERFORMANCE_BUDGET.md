# 負荷予算と計測

**計測環境**：このリポジトリの開発環境にはGPUがありません。数値はSwiftShader（CPUでのWebGL2描画）を使い、`window.__satoyama.breakdown()` で集計した三角形数です。fpsは実GPUで計測していないため、60fpsの達成は**未確認**です。

## 2026-11-18（後半）：描画構造からの軽量化

「景観・地形・運転機能を維持したまま、描画構造から抜本的に軽量化」への対応。解像度や密度を一律に下げるのではなく、描かなくてよい物・更新しなくてよい物・送らなくてよいデータを減らした。変更の前に、6場面×3動作で重さの内訳を測ってから手を付けた。

### 目標と、計測した環境

| | 品質「軽量」 | 品質「標準」 |
|---|---|---|
| 想定する端末 | ノートPCの内蔵GPU（Intel Iris Xe クラス） | デスクトップの中位GPU（GeForce GTX 1660 / RTX 3050 / Apple M1 クラス） |
| ブラウザ・解像度 | Chrome（最新）、1920×1080（描画は0.75倍＝1440×810） | Chrome（最新）、1920×1080（描画は等倍） |
| 目標 | 安定30fps | 60fps |

**実GPUでは計測していない。上の目標は達成を確認していない。** 計測は、このリポジトリの作業コンテナ（4 vCPU、GPUなし）、Chromium 153 headless、ANGLE + SwiftShader（CPUでWebGL2を描く）で行った。SwiftShaderでは頂点処理と画素処理がどちらもCPUで動くので、1フレームが数秒〜数十秒かかり、実GPUの時間とは比べられない。下の表のうち、描画回数・三角形数・CPU側の時間・メモリは環境によらない比較になる。フレーム時間とGPU時間は「同じ環境での前後比」として読む。

### 計測の方法

- `window.__satoyama.profile()`（`src/engine/profiler.ts`）：1/60秒の固定ステップで動かし、1フレームごとに、主パスと影パスの描画回数・三角形数（系統別）、CPU側の更新（物理・各システム）、影・主パス・各画面効果の時間、メモリの推定を記録する。Chromeの `gl.finish()` はGPUを待たないので、1画素の読み戻しで待つ。
- `tools/perf/profile.mjs`：6場面（村・棚田・林道・川・展望・運転席）× 3動作（停止・90°/秒の旋回・7.8m/秒の移動／運転席はアクセル全開）。320×180で描画回数・三角形数・CPU時間を、1280×720でパスごとのGPU時間を測る（`STAGESYNC=1`）。SwiftShaderが遅いので、旋回は4ステップに1回、移動は6ステップに1回だけ描き、CPU側は毎ステップ動かす。
- `tools/perf/ablate.mjs`：展望で系統を1つずつ消し、主パスと影パスの時間の差を見る（1フレームずつなので±300ms程度ばらつく）。
- `tools/perf/physics-step.mjs`：各場面で物理エンジンの1ステップの時間。
- 変更前は `main` に計測の道具だけを足したコミット（6017afa）を、変更後はこのブランチを、どちらも本番ビルドにして別のポートから同じ条件で測った。結果のJSONは `artifacts/perf/`、表は `node tools/perf/summarize.mjs 前.json 後.json` と `node tools/perf/gpu-table.mjs 前.json 後.json`。

### 結果（品質「軽量」）

軽量品質の前後比較（同じ6場面、フレーム数を減らした計測）は、PRを作った時点でまだ計測中で、ここには入っていない。結果は `artifacts/perf/before-low-counts.json`・`after-low-counts.json` として後から追加する。

### 効いた変更

1. **物理の衝突物を近くだけに**（CPU、最大の効果）：木の幹12万本の衝突判定が物理ワールドに常駐し、1ステップ（毎フレーム、止まっていても）に約20msかかっていた。幹を32mの区画に分け、歩く人物か運転中の車の周り（各方向3区画、96m以上）だけを入れるようにした。約0.3msになった。近くの衝突は以前と同じ。
2. **影の遠い段をキャッシュ**：カスケードを距離で選ぶようにし、遠い段はカメラ中心の正方形にして、6%動くか太陽が動いたときだけ描き直す。影パスの描画回数は約4分の1、三角形は約3分の1。建物の影の代役は2つの `BatchedMesh` にまとめて段ごとに選び、木は近い段の光の視野に入るものだけを近い段に描く。
3. **地形をRTINに**：地形の描画回数は、村で主パス261（近景219＋遠景42）→27、影パス202→23。頂点・索引のメモリ（推定、場面全体）は341MB→194MBで、減った分の大半は地形（以前は37.5mの区画を最も細かい格子で全部持っていた。約120MB）。遠景（220m先）は焼いた色のテクスチャ1枚で描く軽い材質。展望で地形のGPU時間が約6分の1。
4. **遠景の木を区画に**：地図の外の山の木（18万本）と地図内の木（12万本）を区画に分け、視野外を描かない。900m先から間引く。地図外の木のGPU時間がほぼなくなった。
5. **草・稲を生える所だけに**：格子の全株を送って潰す方式から、区画ごとに実際の株だけを置く方式へ。稲の葉先の層を1枚の面の中で描く。
6. **画面効果**：全画面パス6本を、半解像度のAO・光芒、縮小バッファのブルーム、最後の1本に。画面効果の合計GPU時間が約3分の1〜5分の1。
7. **更新と転送**：木・小物の行列は一度だけ作り、使う範囲だけ送る。停止中は何も再計算しない。水路の細片（数百の描画）を1つに。シェーダーは最初に全部コンパイルする。

### 画質への影響

同じ条件（標準・1280×720・18:00）の比較画像は `artifacts/perf/compare/`（左が変更前、右が変更後）。
- ほとんどの場面（棚田の縁・水田・林内・集落・川・運転席）は見分けがつかない。草の株は位置の乱数が変わったため、近景の株の配置が少し違う。
- 1km以上先の山の森林は、間引きのため少し淡く、疎らに見える（`overall.jpg` の右奥、`village.jpg` の左奥）。最初の版は450m先から間引き、600m先で焼いた樹冠の法線を読まなくしていたため、中景の山が暗く疎らになった。比較で見つけて、900m先からの間引きに改め、法線は常に読むように戻した。
- 地形の簡略化は1080ラインで約1.5画素（実測の最大誤差は設定の約2倍まで）。畦・棚田の段差の頂点は残る。
- 影：遠い段の解像度は以前の視野に合わせた段と同じ（標準で1m/2テクセル程度）。運転中の連続画像（`tools/perf/drive-shadows.mjs`）で、遠い段を描き直す前後に影の飛びやずれは見えなかった。

### 未達と残る問題

- **実GPUでの60fps（標準）・30fps（軽量）は確認していない。**
- SwiftShaderでは主パスの画素処理（地形・建物・木のビルボード・稲）がまだ大半を占める。実GPUで同じかは分からない。
- 建物（`BatchedMesh` の材質ごとの描画、汚れのシェーダー）は、この計測では差が出なかった。
- 影の近い段は毎フレーム描く。木のメッシュLODが近い段の大半を占める（林道で影の三角形約180万）。
- 起動時の読み込みは約37秒（SwiftShader）で変わらない。テクスチャ圧縮（KTX2）は、読み込み時間・メモリ不足が原因と確認できていないので入れていない。

## 主な最適化（2026-11-18 時点の構造）

- **地形**：14×14ブロック（150m）を、高さの誤差つきのRTINメッシュで描く（`src/world/rtin.ts`）。誤差は地図全体で一度だけ計算するので、同じ段のブロックは境目の頂点が一致する。段の違う境目はスカートで隠す。誤差は距離に応じて決め（標準で1080ラインの1.5画素、耕作地は3倍厳しく）、畦の頂部・棚田の段差・道路と水路の縁は頂点が残り、平らな田面と一様な斜面は大きな三角形になる。400m先は2×2ブロックを1つのメッシュ（300m）にまとめる。220m先（標準）は、読み込み時に焼いた色と遮蔽のテクスチャ1枚で描く軽い材質。法線は1793²の法線テクスチャ。衝突判定は高さ場のまま（表示だけの簡略化）。
- **影**：カスケードはカメラからの距離で選ぶ。近い段は毎フレーム視野に合わせて全部の物を描く。遠い段はカメラを中心にした正方形で、木・建物・山だけを描き、カメラが段の大きさの6%動くか太陽が動いたときだけ描き直す（1フレームに1段まで）。建物の影は模型ごとの代役（遠景モデルの不透明部品をつないだもの）を2つの `BatchedMesh` にまとめ、段ごとに配置1つずつ視錐台で選ぶ。木は近い段の光の視野に入るものを先に並べ、近い段はそれだけを描く。
- **樹木**：樹種×変種×LODごとのInstancedMesh。行列は読み込み時に一度だけ作り、カメラが動いたときに範囲内の分をコピーして、使う範囲だけGPUへ送る（LODの部品同士でバッファを共有）。
- **遠景の樹木**：起動時にLOD0から焼いたビルボード（アルベドと法線のアトラス）。地図の中は300m、外は650mの区画に分け、視野外の区画は描かない。遠い区画ほど、ランダムな順位の先頭の一部だけを描き、残った木を少し大きくする（林のまとまり）。600m先は焼いた法線を読まない。
- **草・稲**：区画（12〜20m）ごとに、生える場所の株だけを読み込み時ではなく区画が近づいたときにCPUで置く（位置・地面の高さ・大きさ・色を属性に持つ）。視野外の区画は描かない。足もとは写真の草株（16m）、その先は4枚×3節の葉（27m）、さらに3枚×2節の疎な葉（42m）、その先は地面の草のテクスチャ。遠めの稲は基底層1枚で、葉先の3層は画素ごとに視線の通る位置を調べて描く。
- **下層植生・畑の作物**：96mのタイルに分け、160m（作物は260m）先は描かない。
- **小物（岩・シダ・ヨシなど）**：32mの格子。行列は一度だけ作り、2m動くごとに範囲内の分をコピーして使う範囲だけ送る。
- **建物**：全模型の部品を材質ごとに `BatchedMesh` にまとめる。家と納屋は近景・遠景の2モデル。110m（標準）より遠くは壁の汚れや凹凸のノイズと法線マップを省く。
- **画面効果**：SSAOと光芒は半解像度、ブルームは縮小バッファの連鎖、最後の1回の全画面処理でAO・光芒・ブルームを重ね、トーンマップと仕上げ。
- **CPU**：動かない物の行列は一度だけ作る。止まっているあいだは木・建物の距離判定もしない。ミニマップは動いたときだけ描き直す。シェーダーは最初のフレームの前に、隠れている物の分も含めて全部コンパイルする。
- **建築のGLB**：頂点を溶接し、KHR_mesh_quantizationで量子化（24MB→5.7MB）。
- **Poly Havenの小物・植物**：meshoptimizerで削減し、テクスチャを512²にしている。複数の個体が並んだ原本（シダ・低木・雑草・苔むした岩）は1個体ずつに分け、1回の配置で1個体だけを描く。
